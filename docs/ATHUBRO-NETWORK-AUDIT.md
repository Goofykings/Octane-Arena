older party/network code would remove current functionality and does not supply
GitHub Pages signaling. No reference code, credentials, old UI, physics, profiles,
maps or game modes are copied.

Keep the existing PartyClient, RtcPeers, NetworkClient and authoritative worker.
The independently useful Phase 3 work is to expose diagnostic states and verify
an automatic bidirectional probe/reply before starting a match. This supplements
the current implementation; it must not be described as a reference-code port.
A real port requires the commit/file containing the claimed WebRTC implementation.

API. Players stay on the normal Pages URL and never type an IP or SDP. Administrator
configuration and the two-device procedure are documented in WEBRTC-MATCHES.md.

## Connection proof and normal-URL diagnostics

The current transport now performs a small automatic `rtc-probe` / reply exchange
on the reliable control DataChannel. Each peer sends its own nonce, receives the
remote nonce and replies, and receives a reply to its own request. Gameplay-ready
requires the existing three open channels, a connected RTCPeerConnection, and
this bidirectional proof. Physics, snapshots, replay channels, roles and signaling
transport are unchanged.

On the normal game URL, open DevTools Console and run:

```js
const report = window.octaneArenaNetwork.diagnostics();
console.table(report.peers);
```

The report includes offer/answer milestones, created/sent/received ICE counts,
ICE/signaling/peer state, all three channel states, probe/reply counters,
`bidirectionalVerified`, round-trip milliseconds and a bounded event history.
It retains eight closed connection summaries for leave/reconnect inspection.
No SDP, candidate addresses, API session tokens or TURN credentials are exposed.

## Administrator setup still required for public Pages parties

The reference does not provide a public signaling service to copy. Your current
project uses its own Node/Fastify API. Hosting it yourself requires no third-party
signaling account, but it must have a public HTTPS address reachable by both
computers. The API must allow `https://goofykings.github.io` as the frontend origin.

Backend environment:

```dotenv
NODE_ENV=production
MATCH_TRANSPORT=webrtc
FRONTEND_ORIGINS=https://goofykings.github.io
HOST=0.0.0.0
PORT=8787
```

Serve it through the existing HTTPS/proxy deployment described in
`docs/PUBLIC-PARTIES.md`; do not make players visit that API address. Set the
GitHub repository **Actions variable** `VITE_API_URL` to the HTTPS API base URL
(without `/api/party`), then deploy the frontend. Alternatively, administrator-owned
`public/config.json` can supply `apiUrl`. The normal Pages URL remains unchanged.
This is one deployment setting, not an IP address each player types.

The API supplies STUN configuration. `STUN_URLS` may override its current defaults.
For networks that cannot connect directly, configure your own/compatible TURN
service using backend-only `TURN_URLS` and `TURN_SECRET`; `ICE_POLICY=relay` can
force a relay test. The server issues temporary credentials. Never put the TURN
secret, database credentials or private deployment keys in frontend variables.
No TURN server/account or public HTTPS API has been provisioned by this change.

## Exact two-physical-device verification procedure

After the updated frontend and public API are deployed:

1. Computer A opens https://goofykings.github.io/Octane-Arena/ normally.
2. Computer B opens the same URL, ideally on a different Wi-Fi/network to test NAT.
3. A clicks **Create Party** and tells B only the six-character party code.
4. B clicks **Join Party**, enters the code and joins. Both see both members.
5. On each computer, open DevTools Console and inspect
   `window.octaneArenaNetwork.diagnostics()`.
6. Require peer `connectionState: connected`, ICE `connected` or `completed`,
   all channel states `open`, `bidirectionalVerified: true`, and nonzero
   probes/replies sent and received. Check opposite host/guest roles and peer IDs.
7. B leaves. Both consoles show no active peer and a closed connection summary;
   A's party UI removes B. B rejoins the same code. Require a new connection ID
   and another successful probe/reply exchange on both computers.
8. Try an unused valid-shaped code; require a clean Party Not Found message.
9. Start Match from the host and verify the same selected mode/arena loads for both.

If the API/party connection is offline, fix deployment/signaling first. If party
membership works but ICE fails, inspect STUN/TURN/network accessibility. A TURN
relay is a WebRTC connection through a relay, not proof of a direct NAT path.
Automated isolated-browser tests on one machine do not prove this physical-device
procedure, public Internet reachability, or operation on every Wi-Fi network.
